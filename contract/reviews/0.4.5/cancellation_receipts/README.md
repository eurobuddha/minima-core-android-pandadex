# Durable cancellation receipts — 2026-09-10

**505 JVM tests pass**, zero failures/errors/skips. Release lint: zero errors/75 warnings. Fourteen new regression methods cover the cancellation journal, recovery and compact evidence. No APK, emulator, user device or node was used. Source remains0.4.5/405 and frozen0.4.4 is unchanged. Prior Android audits apply to their archived source checkpoints.

## Findings and fixes

**HIGH — Cancellation receipts depended on a UI success callback after submission.** MainActivity's single/batch cancellation paths and maker listener appended Pending rows only after node acceptance. A lost reply or process death could leave no receipt; background maker cancellations did not consistently create those UI-owned rows. A failed late receipt append could also interrupt the caller after an already accepted transaction.

DexTxn.cancel and cancelBatch now attach the durable receipt wrapper centrally before postGated. Size-one batches use the existing single-cancel delegation. The wrapper reuses creationResult's journal as a shared intentResult implementation: every cancellation source gets a stable receipt UUID, original order identity/economics, source coin ID, common transaction handle, submission block/time and phase. One acknowledged Pending save stores the whole batch at PREPARED before signing. POSTING must be saved for every source before txnpost is allowed. Rejection of preparation, caller refusal or failed required persistence refuses the dependent step.

After acceptance, SUBMITTED and the returned ID are recorded when possible. If that status write fails, the already durable POSTING rows remain recoverable and the caller still completes. Unknown post outcomes remain UNKNOWN; failure before posting is NOT_SUBMITTED. Completion callbacks run once. A late batch reply updates only surviving rows, never recreating sources already resolved on-chain. The old UI-only cancellation inserts are removed, avoiding duplicate receipts and moving background/manual/maker cancellation onto the same path.

The existing linked-input/refund history verifier still decides the outcome. New receipts additionally compare the included input against the saved source's owner, payout, tokens, amounts, direction, order ID, GTC flag and minimum remainder. A changed source balance cannot prove the requested cancellation. NOT_SUBMITTED rows are retained as such and are not reclassified as later mining/trading outcomes. Old accepted-only receipts remain compatible with the existing linked-input history path. Confirmation remains evidence of the source order's refund/fill outcome, not proof that a particular retry or locally returned TxPoW ID was the winning transaction.

**Storage optimization:** cancellation evidence stores only the effective source fields used by that proof, following the owner-relock builder's state mapping. Display-only port6, extra state, token artwork and unrelated node metadata are excluded. A test with2MB token metadata plus100KB unused state confirms the saved source remains under2KB for the fixture, with unchanged economic matching. This is a compact expectation snapshot, not a byte-for-byte archive of the node reply.

## Reuse and validation

Inspected/reused Pending.creationResult, synchronized load/save, its acknowledged PREPARED/POSTING transitions, stable receipt identities and non-resurrection behavior. The original creation tests run against the shared implementation. DexTxn's existing cancel/cancelBatch transaction layouts, SignGate, CoinLock, txncheck and beforePost checks remain unchanged. DexHistory's input-index refund/fill verifier and owner-relock equality checks supply the proof rules. CreationEvidence's compact intended-state storage and Order5's parsed fields supply the compact snapshot approach. Searches of sibling PandaPools/UTXO cancellation and intent code did not expose a more compatible batch journal than the existing PandaDEX creation implementation.

Fourteen tests cover atomic batch prepare, failed prepare/posting writes, restart after lost reply followed by linked refund recovery, unconfirmed refund retention, changed original funding rejection, failed accepted-status write with exactly one callback, late replies after partial batch resolution, definite pre-post failure, unknown outcomes without replay, missing batch receipt preventing posting, corrupt store/duplicate input protection, caller quote/permission refusal, real cancel entry points refusing missing receipt storage before node access, and unrelated metadata exclusion. The full505-test suite, including creation, maker handoff and pending recovery regressions, passes.

Node history and transaction completion are deterministic fixtures. Tests do not sign/post on a real node, run Android SharedPreferences/process death, execute a successful production DexTxn chain end-to-end, render the UI, or validate Samsung background behavior. They exercise the real journal/serializer/reconciler with controlled boundaries. Source hashes and saved XML identify this checkpoint.

## Remaining risks

Owner edit/relock receipt creation is still late in the UI path and needs the equivalent durable-intent review. Third-party collectExpired uses a separate maintenance path and is not converted to an owned cancellation receipt by this pass. Other callback-side persistence such as db.forgetMyOrder and rendering can still fail; this change removes the late Pending append hazard, not every caller exception path.

The receipt store still needs broader malformed-row validation, long-term growth management and recovery/export visibility for raw damaged data. Terminal cancellation history/tombstone retirement and definitive attribution among retries/competing spends remain separate work. General valid-snapshot maker races, legacy reconstruction, failed-pause restart policy, book/ownership freshness, background pairing and actual Android/stock Samsung integration remain open. The human-only composite gate is unexecuted. No production-ready or100%-security claim is made.
