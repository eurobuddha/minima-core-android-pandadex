# PandaDEX 0.4.5 / 405 — recovery work in progress

This is a source checkpoint, not a production approval or a new APK release. The signed 0.4.4 APK and its recorded SHA-256 remain unchanged. Source changes are uncommitted; no user node or device was accessed in this continuation.

## Fixed since 0.4.4

- Pending order receipts no longer disappear after twenty minutes. Delay is recorded once, while the unresolved receipt survives reloads.
- Pending storage reuses PandaPools ActivityLog's synchronized read-before-write pattern. Stable receipt IDs replace Java object identity, and updates from other Activity instances/callbacks are preserved.
- Receipt persistence completes before resolution is announced. Unreadable stored data is preserved rather than overwritten with an empty list, and the trading UI pauses when receipt storage is unreadable.
- Price-edit confirmation no longer relies on a copied order ID appearing in the book. The included transaction must spend the original order, preserve its owner/payout/token/locked amount/state, and produce the requested new want amount. The verifier materializes output state from `body.txn.state`, matching the actual node TxPoW JSON shape. A refund or full fill racing the edit is reported separately.
- Partial fills use actual confirmed payments and remainder amounts. Buy-side rounding can make the payment differ by one smallest unit from the amount inferred by subtracting successor wants. That difference no longer discards a real fill. A misleading full-disappearance hint also cannot inflate the recorded partial amount/price.

- Market-fill candidates now use additive SQLite schema 5, keyed by source coin ID and storing the original parsed coin JSON. The previous 512-entry in-memory drop limit is removed. Each pass reads at most 32 candidates; unresolved rows rotate durably in one transaction so older misses do not starve newer fills. Startup seed scans also trigger recovery exactly once.
- Failed candidate persistence stops the disk book snapshot advancing past that candidate. Corrupt stored candidates and unclassified included spends are retained; storage failures are surfaced to the Activity or background notification rather than silently treated as successful recording.
- Both Activity and background service record a public fill and its personal maker receipt inside the same SQLite transaction. A replay can restore a missing personal row even if the public row already exists, preserving the public row's original observation timestamp. Notifications happen after commit. Existing personal rows are not rewritten by this repair.
- Recovery waits for fresh wallet ownership data, including a second check after asynchronous history lookup, so a cold start does not classify an owned fill as someone else's trade.
- A partial fill that pays the whole requested maker amount still records the actual consumed amount when an included remainder exists. This matches the frozen V5 script's allowed overpayment behavior; the covenant is unchanged.

- Historical lookup now persists a separate offset per source coin and wallet/public scope in additive SQLite schema 6. Every retry probes recent history before resuming the older search with overlap. Reaching the retained end cycles back for another pass; it never marks an unresolved receipt as failed/nonexistent. Both foreground and service use the shared database-backed history implementation, including pending cancellation/edit and taker reconciliation.
- An oversized newest transaction cannot indefinitely prevent an older saved search from resuming. Replies larger than the requested page are rejected, network/invalid replies do not advance past unread history, and progress-write failure still delivers already verified evidence without leaving callbacks pending. A failed error notification from a closed Activity cannot wedge the fill settler.

- A successor-looking coin with an equal or larger balance no longer suppresses the original order's disappearance as an assumed renewal. Public identity/state can be copied; all such cases now reach the spending-transaction verifier. Actual included owner relocks retire without creating a fill. The relock invariants are extracted from and shared with the existing pending-edit proof, including an explicit match to the original source input.

- Spend evidence now carries the actual inclusion height/block ID and, when retrievable, a verified inclusion-block timestamp. The node's `txpow onchain` block ID is fetched by exact ID; the reply must be a block with the same height/ID and contain the target TxPoW (or be the transaction-carrying block itself). Transaction proposal-header times are not substituted. Missing, malformed or mismatched block data leaves the inclusion timestamp unknown while preserving independently valid inclusion evidence.
- New maker-fill rows use verified block times when available. Observation-time fallback is explicit in receipt notes and labels. Replaying a pre-existing public row preserves its original observation and does not mislabel it as newly verified block time. Old/future-dated fills do not produce fresh-fill notifications. Existing legacy records and taker timestamps are not retroactively rewritten by this change.

- Historical V5 order-spend discovery is now wired into the foreground/service settlement path. It reuses the bounded history pager and exact inclusion verification, inspects valid V5 input coins, and alternates with known-receipt recovery. It can recover fills even when the process never observed their resting order coins. A pass delivers at most 32 discovered orders and stays within the existing page/inclusion budgets.
- Discovery saves each source candidate before advancing or recording. Additive schema 7 persists whether a candidate came from history, so an unknown inclusion timestamp cannot become today's observation time after restart. Such historical trades remain queued until their block time is verified; confirmed refunds/relocks can retire without creating trade volume.
- A separate verified-spend ledger survives public-tape trimming and prevents repeat imports of the same source/spender across restarts. Candidate removal and ledger insertion commit together. A different included spender is retained for reconciliation rather than silently replacing existing proof; automatic reorg repair remains incomplete.
- Additive column migration now checks for an existing column and propagates genuine schema/disk failures instead of swallowing all exceptions as success.

- Manual and background maker creation now share a durable receipt at `DexTxn.createOrder`'s existing pre-sign boundary. The receipt records the selected funding input IDs, exact locked token/amount, all nine intended state ports, payout/change, local handle, and submission phase. A failed commit prevents signing or posting at the corresponding boundary. Definite pre-post failures and uncertain post attempts remain distinguishable after reload; late callbacks cannot resurrect a resolved receipt.
- Creation confirmation now requires an included transaction spending every selected input, with no extra/duplicate funding inputs, and producing the exact covenant output/state and optional state-free change. It no longer accepts owned-book order-ID presence. This also verifies creation when the order was taken before the app observed it. The notification describes verified creation, without claiming the order is still live.
- The Orders screen no longer hard-codes every pending creation as “MINING”. It and Trade render the same persisted evidence state. Old receipts without funding evidence stay visible and explicitly unresolved. This change does not reconstruct absent legacy funding IDs or retroactively repair them.

- Additive schema 8 stores repeat confirmation checks separately from the original trades. Migration registers usable maker/taker TxPoW IDs without rewriting their receipt bytes. New trade/ledger insertion registers its check target in the same database transaction. New ledger entries also retain the original order input JSON for later reconciliation; old ledger records gain an empty column without fabricated evidence.
- `ChainReview` adapts PandaPools `ActivityLog.verifyNext`'s serial lookup pattern through the existing `DexHistory` command seam. Foreground and service settlement run at most eight repeat checks per pass, with a process-wide gate, one callback per request, and early exit on unavailable/malformed replies. Four recent and four older entries rotate by a durable revision. Compare-and-set updates reject stale callbacks.
- An explicit successful node reply saying the TxPoW was not found marks corroboration missing. Transport failures and malformed replies preserve prior proof, including its valid-check timestamp; the latest attempt has a separate timestamp. A node miss is not interpreted as transaction rejection, a reversal, or proof that it never occurred. A later valid inclusion restores corroboration. Confirmations are displayed as the node's last returned count with the valid check time, never extrapolated from wall-clock time.
- Missing-corrobation records remain visible in market tape, personal trades, Orders and exports, retaining original amounts, timestamps and evidence. They are excluded from chart/ticker aggregates, personal net totals and P&L while unresolved. CSV rows retain their original deltas and now carry `accounting_included`; summaries state excluded counts and that reconciliation is provisional. A successful public-explorer lookup cannot override a missing-node recheck, and TxPoW inclusion alone does not upgrade legacy trade-effect evidence.
- A conflicting included spender now reports a reconciliation issue instead of a misleading “free device storage” error. The later schema-9 correction path below can resolve the source/maker record when the required ordered evidence is available.

- Schema 9 adds a permanent correction archive and an explicit non-trade marker for market rows. Before changing a source/maker record, the store preserves the earlier ledger, public/personal records, prior check, exact replacement input/outputs/state, inclusion coordinates/time and proof order. A different stored spender can be replaced only after it was explicitly missing and the replacement was subsequently verified in the same running process. Missing-time/incomplete evidence is retained for retry. First complete linked proof can also correct legacy source/maker records without a ledger; this does not infer a transaction from a copied ID or book disappearance.
- Proof ordering uses a process epoch and monotonic sequence, captured when the inclusion reply arrives rather than when a delayed block lookup finishes. Restart requires a new prior-spender check. Accepted settlements update the guarded current proof, preventing an obsolete miss from surviving a return to the chain. Newer misses or changed inclusion blocks reject stale settlement callbacks; revision guards protect concurrent check callbacks.
- Both hosts route fill/non-trade settlement through the same database boundary. Correction archive, updated public/personal data, new winner and candidate retirement commit together. Notifications occur after this commit; a correction cannot generate a fresh-fill alert. A failed correction rolls back as one unit. Repeated source retirement avoids rewriting an already completed winner.
- A confirmed refund/relock correction retains the earlier trade row with an explicit superseded/non-trade status, excluding it from volume and accounting. A corrected maker fill uses its new proven amount/time, retaining its predecessor in the archive. Maker corrections explicitly require `maker=1` when updating personal rows: an aggregate taker receipt can share its first source-coin key and must not be rewritten as a maker fill or refund. Broader taker/composite correction still needs its own full-input/payout proof.
- The Trades screen now includes Corrections with prior amounts/times and source/old/new TxPoW IDs. It reads compact summaries, rather than loading every archived transaction payload into the UI. Personal exports include `corrections.json`, read in the same database snapshot as the current rows and preserved through optional explorer corroboration. Full original data is retained; no old APK or frozen validation archive was overwritten.

## Explorer receipt boundary — subsequent source hardening

`ExplorerVerifier.java` previously accepted any positive `block_number`, even when the returned record belonged to another TxPoW, and coerced fractional JSON heights through `optLong`. `TradeExport.java` also replaced the original verification height whenever an external result carried a positive block, including a result whose status was an error. These are now fixed: the existing bounded HTTPS transport retains normal TLS verification, disables redirects, requires one valid tRPC result, matches both returned `txpow_id` and `id` to the requested ID, and reuses `ChainEvidence.positiveLong` for exact bounded heights. The result carries its matched identity through the export boundary.

Exports preserve the original node/local height, timestamp, amounts and evidence. A missing local height is not fabricated from the explorer. Unresolved/superseded rows remain excluded from accounting, and appended notes preserve the original timestamp-basis suffix.

## Export availability — subsequent source hardening

**MAJOR — Fixed:** Every row previously performed a blocking public explorer lookup, even when multiple rows shared a TxPoW; an unavailable/slow service could delay a large export for an unbounded sequence of request timeouts. `ExportChecks.java` now wraps the existing verifier with a 30-second monotonic budget, a ten-second maximum wait for one lookup, at most 128 distinct IDs, and case-normalized reuse of successful or unavailable results within the export. Completed results remain available after the budget ends. Remaining rows retain their full original receipt evidence and carry an explicit note that public explorer corroboration was not completed; no trade rows or correction evidence are dropped.

A dedicated executor permits one physical external request and one queued request. Timed-out queued tasks are cancelled and removed. A DNS/socket operation that ignores interruption continues occupying that sole worker rather than allowing replacement threads to accumulate. This respects Java's [cancellation semantics](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Future.html): cancellation attempts interruption; it is not proof that the underlying operation stopped. The next export can still return its local records if the external worker remains unavailable.

**MAJOR — Fixed:** Repeated export taps could enqueue duplicate builds and replace the outstanding save callback. `TradeExportWriter` now admits only one build at a time process-wide; `MainActivity` guards its complete build/picker/save flow, resets on cancellation/failure, and reuses PandaPools' picker-launch exception cleanup. Writing to the user-selected document provider is dispatched to the existing export worker, so a slow provider no longer writes the ZIP on the main thread.

Nine new JVM test methods verify deduplication (including errors), actual remaining-budget propagation, deadline/ID-limit handling without receipt loss, invalid-ID rejection, interruption/error behavior, and a real non-interruptible worker with repeated queued timeouts and recovery. **386 JVM tests pass; release lint has zero errors and 76 warnings.** No APK was built. ## Automatic aggregate repair — schema 11

**MAJOR — Fixed for receipts with retained complete expectations:** Archived taker receipts now enter bounded recovery when accepted node checks report a missing or changed inclusion. `TakerRecovery` reuses the existing wallet-history pager, exact all-selected-source/payout matcher and verified block-time evidence. A stored receipt is never itself a fresh proof. Missing legs, different immutable identity, incomplete time or pruned/unavailable history retain the original queued receipt.

`DexDb.repairTaker` compares the retained snapshot inside its write transaction, checks original expectations and economics, and applies the existing ordered-proof guards. It repairs inclusion height/time, same-height replacement blocks and a different mined TxPoW for the same immutable transaction. A changed TxPoW additionally requires an earlier explicit miss and later full proof in the current process epoch. Newer contradictory checks reject delayed callbacks. Original row/evidence, new proof and prior check enter Corrections before the personal row, current evidence, confirmation check and queue flag commit together. Write failure rolls everything back. Repair preserves amounts, ownership and effect classification; summary source metadata can be restored from the retained intent. Completion retries reuse this boundary, while legacy rows gaining their first archive must match source metadata as well as economics.

Pending aggregate repair is visible in receipt notes and excluded from provisional accounting until full proof succeeds. It does not erase old rows or show the changed TxPoW alone as a repaired trade. A successful repair restores the original eligibility without generating a fresh-fill notification or promoting a superseded effect status.

The shared Activity/service path alternates aggregate and market recovery using a persisted turn, including across host recreation. At most four aggregate receipts/eighty selected source IDs enter a pass; existing history-page/inclusion budgets remain in force. A process-wide gate and duplicate-callback guard prevent overlapping aggregate work. Schema 11 adds a durable pending flag/retry order and `takerreceipt_review` index. Accepted rechecks queue indexed work in their own transaction; a queue failure rolls back that recheck too. Empty aggregate queues allow market work immediately.
